# x402 for Stellar Intel — Does Metered Per-Request Payment Fit?

**Last reviewed:** 2026-08-29

**Status:** Research / recommendation
**Context:** Metered API access for agent callers ([#1054](https://github.com/ezedike-evan/stellar-intel/issues/1054))
**Date:** 2026-08-29

This note answers three questions: what x402 requires of a server, whether a
Stellar-settled variant is viable today, and which of this product's surfaces
would be metered — ending in a do/do-not recommendation. No implementation is
proposed here beyond naming the seams one would use.

---

## 1. Problem

The product is an agent-facing intelligence API with no payment concept
anywhere in the code: every public endpoint is anonymous, guarded only by a
fixed-window per-IP rate limiter (Postgres-backed, `lib/api/rate-limit.ts`),
and there are no API keys, accounts, quotas, or billing tables. The roadmap
carries exactly one monetization item — #233 "Rate limits + API-key tier
(free / paid)", unchecked — and the docs index already promises "rate-limit
tiers" the auth page does not deliver. Meanwhile the declared primary callers
are AI agents (over MCP and the REST API), which is precisely the caller
class that cannot hold a credit card but can hold a wallet.

x402 is the HTTP-native answer to that shape: the server responds `402
Payment Required` with machine-readable payment requirements, the agent
retries with a signed payment authorization, and a facilitator verifies and
settles on-chain — no accounts, no keys, no signup. The question is whether
it fits _this_ product, on _this_ chain, _now_.

---

## 2. What x402 requires of a server

The protocol (v2, now governed by the Linux Foundation's x402 Foundation) is
deliberately small on the server side:

1. **A 402 response** carrying Base64-encoded payment requirements — accepted
   scheme, price, network, destination address — when an unpaid request hits
   a metered route.
2. **A retry path** that reads the client's Base64 payment payload header,
   `POST`s it with the requirements to a facilitator's `/verify`, serves the
   request on success, then `POST`s `/settle` and attaches the settlement
   result header to the response.
3. **A facilitator relationship** (or self-settlement). Hosted facilitators
   expose `/verify`, `/settle`, and `/supported`; the server holds no keys
   and touches no chain directly.

Everything else — schemes, wallets, signing — is client- and
facilitator-side. A server integration is middleware plus configuration: a
receiving address, a price schedule, and a facilitator URL.

## 3. Is a Stellar-settled variant viable?

**Yes — this stopped being hypothetical in March 2026.** The issue's framing
("reference implementations are EVM-first") predates the current state:

- The Stellar Development Foundation is a **Premier member of the x402
  Foundation** with a Governing Board seat, and Stellar's developer docs ship
  a first-class x402 guide.
- A **production facilitator exists** (Built on Stellar, on OpenZeppelin
  Relayer): testnet and mainnet endpoints under `channels.openzeppelin.com`,
  with network fees covered. Coinbase's hosted facilitator also lists Stellar
  testnet with sponsored fees.
- An official **`@x402/stellar`** npm package implements the `exact` scheme
  via Soroban signed auth entries; payment assets are SEP-41 tokens with
  USDC as the default (issuer and contract ids published for both networks).
- Stellar's economics fit micropayments unusually well: ~$0.00001 fees,
  facilitator-sponsored at that, and USDC/PYUSD as native (not bridged)
  assets.

**The constraint that matters:** clients must sign Soroban auth entries. The
supported signer list is browser-extension wallets (Freighter, Albedo, Hana,
HOT, Klever, OneKey) plus anything that can sign programmatically via the
SDK. For _agent_ callers — ours hold keypairs, not browser extensions — the
SDK path is the relevant one and it exists. For human browser traffic it
would exclude mobile today; irrelevant here, since humans use the web UI,
not the metered API.

## 4. Which surface would be metered

**REST is the natural first surface.** There is no global `middleware.ts`
(coverage is deliberately per-route), and the two shared seams every guarded
route already funnels through are exactly where a 402 slots in:
`enforceRateLimit()` returns a prebuilt 429 (`rateLimitedResponse()` is the
template a `paymentRequiredResponse()` would mirror, headers and envelope
included), and `withV1()` wraps the hardened v1 surface. The natural
composition with the existing fixed-window limiter is **pay-to-exceed**: the
free per-IP allowance stays exactly as it is, and the 429 a caller hits
past it becomes a 402 offering the paid continuation. Nothing about the
free tier changes; the price only ever buys headroom.

**MCP is real but second.** Upstream patterns for 402-inside-MCP exist
(Vercel's `x402-mcp`, an official guide in the x402 docs), and the tool
inventory here is exactly the kind that gets monetized elsewhere. But this
repo's MCP has structural gaps to close first: the stdio transport has no
HTTP layer to return 402 on at all; the streamable-HTTP transport is a raw
`node:http` server outside Next with **zero auth and zero rate limiting**
today; and three of the five tools call the library **in-process**,
bypassing every REST-side control — so REST metering would not meter them.
Metering MCP means building its enforcement layer from scratch, which is a
bigger decision than adopting x402.

**A blind spot either way:** no telemetry distinguishes MCP-originated from
direct REST from browser traffic, and the MCP package emits no usage
telemetry at all. Nobody can currently say which surface has traffic worth
pricing.

---

## 5. Recommendation

**Do — narrowly, testnet-first, and not as a paywall.** The protocol fits
this product's caller class, the Stellar rails are production-real, and the
server-side cost is small because the 429 seams already exist. But the
product's adoption posture is "free, anonymous, agent-friendly", and pricing
a pre-traction API strangles the very agents the roadmap courts.

### Buildable now (recommended path)

A pay-to-exceed experiment on one expensive REST route (`/api/rates` is the
costliest read), behind the existing `enforceRateLimit()` seam: free window
unchanged, 402-with-requirements instead of a bare 429 past it, settled in
testnet USDC through a hosted facilitator, env-gated off by default. This
answers the questions research cannot — do agent callers carry x402 clients,
does the facilitator hold up, what does a sane price look like — while
risking nothing: an agent without x402 support sees today's behavior.

**Trade-off:** a facilitator dependency and a receiving-address custody
decision enter the operational surface for a feature that earns testnet
tokens. That is the price of learning with real callers.

### Wait on evidence

Mainnet pricing, and any MCP metering, wait on two things: per-surface usage
telemetry (currently derivable only from request logs, and not at all for
MCP), and an enforcement layer for the MCP HTTP transport, which today has
no auth story for a 402 to compose with. Revisit #233 when the experiment
reports: x402 may _be_ the paid tier, making API keys unnecessary for
machines — keys then matter only if human organizations want invoices.
